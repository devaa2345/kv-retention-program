# Tight-KV latency and compute accounting: measurement plan

This is a prospective timing study of the frozen two-pass M2/M3 SQuAD system in `PREREG_REALTEXT_TIGHT_KV_M2_M3.md`. It does not change, rerun, or rescore the committed accuracy results. The three timed arms are plain floor, equally focused floor, and two-pass focused SnapKV, using their frozen prompts, pointers, masks, retention rule, and greedy generation. Floor's plain arm has **one prefill only**: it receives no artificial or “wasted” second pass. This asymmetry is the cost being measured.

## Cost definitions and phase boundaries

Report seconds per query for four mutually exclusive phases. **First prefill** includes context retention/compression at `B0`, its device forward, original A1 query tokenization and query forward. **Pointer selection** starts after the synchronized A1 logits and includes attention extraction or lexical sentence ranking plus focus-query construction; plain floor has zero pointer time. **Second prefill** includes final-budget calculation, context retention/compression at `Bfinal`, its device forward, focused-query tokenization and query forward; plain floor has zero second-pass time. **Generation** begins with the first answer-token decision and ends at EOS or the frozen cap, including literal-mask work for focused arms. Device synchronization separates phases. Input-file reading and offline instance construction are outside the per-query clock. The first context prefill is shared by an instance's two questions in the original implementation; attribute half its measured time to each question in every arm, while retaining the raw shared measurement for audit. All query-specific work is charged to its query.

Record three distinct clocks, without relabeling one as another: (1) synchronized, post-model-load elapsed processing time, comparable to the “GPU processing minutes after load” used in the accuracy reports, **which includes CPU work and is not device-only GPU time**; (2) CUDA-event elapsed device time for each GPU phase, with pointer's CPU time separately shown; (3) outer process wall time, including WSL startup and model loading, reported separately from the warm per-query comparison. The primary per-query wall ratio is mean synchronized warm query time for the focused arm divided by mean synchronized warm query time for plain floor. Report the full-job wall and startup/load contribution explicitly; do not silently amortize a one-time startup stall into a query. Record output-token counts and stop reasons so different decode lengths can be interpreted. Report mean, standard deviation, median, and range per phase and arm, plus instance-paired differences and intervals for total times. Use the same hardware and runtime settings for all arms within a model, rotate arm order by a fixed seed, and warm up each arm on separate timing-only queries.

## Architectural expectation and diagnostic gate

The second pass reprocesses approximately the whole 2,000-token context, not merely the approximately 45-token reinserted sentence. The sentence is about 2.25% of the context, implying only a few percent *increment within that second pass* from token count alone; it does **not** imply 2.25% total latency overhead. Expect roughly one additional context-prefill's device work per focused query (broad sanity interval: second-pass median CUDA time between 0.5 and 2 times the first-pass context CUDA time after accounting for the shared first pass). Pointer wall time should be smaller than the second prefill. Total latency can depart substantially from a twofold ratio because generation, CPU compression, attention extraction, and prompt preparation also cost time. These are bug-detection bounds, not a claimed result. If the bounds fail or timing is unstable, diagnose and stop before scaling; do not revise the expectation after seeing the data.

## Deferred execution plan

First use eight new timing-only SQuAD instances, two queries each: **16 paired queries per arm per model**. Select sequential candidates after index 1217 using the prior unused-question filter; hash and save the manifest before running. Do not reuse any frozen accuracy query. Run M2 and M3 on the same pilot queries. Time the actual frozen inference workload, but do no accuracy scoring and do not treat generated answers as accuracy observations. Require complete phase traces, verified one-pass plain floor and two-pass focused arms, valid equal pre-answer KV, and synchronized clocks. Report pilot spread and the architectural check before deciding to scale.

If the pilot is plausible and stable, select a fresh, nonoverlapping final timing set once. Let `s²` be the pilot variance across *instances* of the mean of their two paired query wall-time differences (focused SnapKV minus plain floor, and focused floor minus plain floor), separately for M2 and M3. Let `δ=0.10 ×` that model's pilot plain-floor mean warm query time. Set `N_required=ceil((1.96+0.84)^2 × max(s²/δ²))` over the four model/comparison pairs, then use `N=max(32,N_required)` instances. If `N_required>160`, report the required size and cost before deciding whether a full run is practical; do not present a capped, underpowered run as resolved. Freeze the final manifest, code hash, and N before running each arm once. Report paired instance-bootstrap 95% intervals for absolute and percent time overhead; resample instances, never individual questions. The precision calculation concerns a 10%-of-floor timing difference, not accuracy power.

For each model report added warm wall seconds/query and percent of plain floor, added post-load processing seconds/query and percent, device-time components, and full-job wall including startup/load. Show whether overhead concentrates in second prefill or another phase. Pair the already committed accuracy gains (+13.75 points M2 and +27.50 points M3 over plain floor) with the **measured** warm-wall ratio, without recomputing accuracy. This timing test does not compare against a hypothetical single-prefill method that could reach the same accuracy, and it does not amortize the first pass across a multi-turn session. Those remain open questions for later work, not adjustments to this cost result.
