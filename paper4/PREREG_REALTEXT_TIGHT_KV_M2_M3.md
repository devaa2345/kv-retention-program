# Per-query KV-paid SQuAD focus: M2 first, then M3

This is a new, prospective test of the harder claim: **focused SnapKV beats plain full-budget floor when pre-answer KV tokens are exactly matched per query**. Beating an equally focused floor is a required secondary control, not sufficient for the headline. Prior extra-KV M2/M3 wins and the M2 fixed-128 reserve result motivate the test but are spent data, not its confirmation. No RTX Pro 5000 run is planned.

## Frozen method

Use `out/_realtext_tight_generate.py` unchanged for both models. For each query and retention arm, `B0=round(0.2802*n_ctx)`. The first context prefill at B0 is a **scout**. Run the unchanged A1 query and select one eligible source sentence with floor's last-token attention or SnapKV's BM25 lexical pointer. Record the plain unmasked answer for that arm. Discard the scout cache. Construct the unchanged focus query, measure its exact model-tokenizer post-prefill cost `e`, and prefill again at `Bfinal=B0-e`. Keep the scout-selected sentence fixed, without reselecting on the final cache. Run the focus query against the final cache and decode with `literal_v1`. If `Bfinal<=SINK+WINDOW`, use the original A1 query with the same selected-sentence mask and B0, recording a fallback. Both arms get identical two-pass treatment. The scout and final compressed caches must never coexist.

The code asserts `Bfinal + actual_focused_post_tokens == B0 + original_A1_post_tokens` for every query. Thus focused and plain arms have **equal KV token counts before the first answer token**, within each model. This is not a claim of equal compute or generation-stage memory: there is a second prefill, and answer lengths can differ. Record extra tokens, both keep-set hashes, scout and final gold-sentence retention, whether the scout-selected sentence survives in final cache, fallback, peak allocated GPU memory and processing time. Use the same A1 prompt, model, tokenizer, sink/window, 0.2802 base ratio, strict whole-answer exact score (casefold and whitespace-run normalization only), and literal_v1 mask as prior work. No gold answer enters the pointer or allocation rule.

## Confirmation decision rule

Four arms per query: plain floor, plain SnapKV, two-pass focused floor, two-pass focused SnapKV. Require complete paired records, saved prefill-only scout pointer agreement, base/scout keep-hash agreement, exact pre-answer KV equality, source-sentence literal masked output, zero corrected full-context invented values for focused arms, and exact-score recomputation. Use 10,000 paired **instance-level** bootstrap resamples, seed 5070, averaging each instance's two query differences before resampling.

M2 establishes the matched-memory win only if **both** 95% CI lower bounds exceed zero: focused SnapKV minus plain floor (**primary headline criterion**) and focused SnapKV minus equally focused floor (**necessary fairness control**). Report both comparisons, plus focused SnapKV minus plain SnapKV and focused floor minus plain floor, even if one fails. If M2 passes and checks pass, run M3 on the **same already locked fresh confirmation manifest**, with its own tokenizer, unchanged algorithm and identical two-CI criterion; otherwise report the M2 result and stop this two-model test. A two-model matched-memory claim requires all four positive lower bounds. The same manifest across models does not equate their absolute KV bytes or make their outcomes statistically independent.

Before any held-out answer generation, append the chosen confirmation manifest hash, both models' prefill-only scout ceilings where measured, code/score hashes, and measured development GPU time to this file and commit it. Development answer generation estimate is 3–5 GPU processing minutes after load on M2; measure it before estimating confirmation time. Do not edit `CONFIRMATORY_RESULTS.md` while this test is underway.
