# Next fresh-data test: per-query KV-paid focus on M2 and M3

This is a design for a separate experiment, **not a preregistration or result**. The two models now have prospective focused-system wins on fresh SQuAD, but both inserted evidence outside the retained-cache budget. M2's fixed 128-token reserve control passed against an equally focused floor and did not establish a win over plain full-budget floor. A per-query allocation should test that remaining claim without spending a fixed 128 tokens when the focus sentence is shorter.

## Proposed deterministic two-pass method

For each query and retention arm, set `B0=round(0.2802*n_ctx)`. First compress the context with budget B0 and run the unchanged A1 query only to select the sentence: last-token attention for floor, lexical BM25 over SnapKV-eligible sentences for SnapKV. Record the pointer and discard this scout cache. Construct the unchanged focus query and tokenize it to measure `e = focused_post_tokens − A1_post_tokens`. Recompress the same original context at `Bfinal=B0−e`, then run the focused query with the frozen selected sentence and `literal_v1`. Do **not** reselect the sentence on the final cache. The two passes must run sequentially and the scout cache must be released before building the final cache. If `Bfinal` is smaller than the mandatory sink/window plus one additional token, use the original A1 post-query with the same selected-sentence mask and `Bfinal=B0`, recording a fallback. This rule uses no answer or gold text.

At the first answer token, `Bfinal + focused_post_tokens = B0 + A1_post_tokens` exactly whenever focus fits. The scout pass itself has the plain floor's B0 retention budget; no two compressed caches coexist. The method costs a second context prefill and may rely on a sentence selected from the scout cache that the final keep-set drops. Measure and report both effects. Claim exact **pre-answer KV-token equality**, and measure peak GPU memory and compute separately; do not equate the models' KV bytes because they have different head counts.

Both floor and SnapKV must receive the same two-pass rule. Compare focused SnapKV against both two-pass focused floor and one-pass plain floor at B0. Include plain SnapKV at B0 as a within-method baseline. Keep A1, `literal_v1`, strict whole-answer exact scoring, attention and lexical pointer algorithms, and 0.2802 base ratio unchanged.

## Data, sizing and decision proposal

Use a fresh 32-instance development set to implement and validate the two-pass cache release, exact token accounting, keep-set capture, pointer consistency and literal mask on **both models**. This set may diagnose failures but cannot be confirmation. Then lock a globally distinct-question confirmation set of **160 instances / 320 SQuAD queries**, shared across models and unseen in all prior real-text samples, before answer generation. The M2 matched-control observed paired instance variance for focused SnapKV minus plain floor was 0.07831. For a 7-point target, `ceil((1.96+0.84)^2 * 0.07831 / 0.07^2)=126` instances; 160 provides margin while keeping the RTX 5070 run bounded. This is a planning calculation from spent data, not a power guarantee, especially for M3 or if the effect is smaller. Do not use the exploratory M3 artifact's accuracy to choose N.

Before generation, commit the code, development record, manifest hash, prefill-only pointer ceilings, expected GPU time, and exact decision rule. Compute 95% paired **instance-level** bootstrap CIs with 10,000 resamples, seed 5070. A two-model matched-memory claim requires all four lower bounds >0: focused SnapKV minus focused floor and minus plain floor, separately on M2 and M3. Report each model and comparator even if one fails. Also report full-cache length and ratio, actual focused extra tokens, final retained budget, pre-answer KV-token equality, peak allocated GPU memory, final gold-sentence retention, scout pointer hit, final-cache sentence retention, cap stops, raw-substring and corrected invented-value checks, and measured GPU processing time.
